# Parity fixtures

These files check that this SDK returns the same positions as the web SDK
`pdf-signature-esign-sdk` **1.1.2**.

| Path | Contents |
|---|---|
| `pdfs/` | Test documents. `password-aes256.pdf` and `password-rc4.pdf` are `sample.pdf` encrypted with user password `test123` (made with qpdf). `sample.pdf` has A4, A4 landscape, US Letter and a `/Rotate 90` page (generated by `scripts/make_sample_pdf.py`) |
| `scenarios.json` | Actions to run, e.g. `placeSignature({ page: 2, x: 100, y: 200 })`, plus the tolerance (0.5 pt) |
| `web/` | Runs the scenarios with the real web SDK in headless Chrome |
| `expected/` | Web SDK output: page sizes and `getSignatures()` per scenario (item `id` removed) |

## Regenerating the expected output

```bash
cd parity/web
npm ci
npm run expected        # uses Chrome at /Applications/Google Chrome.app; set CHROME_PATH otherwise
```

Then copy `scenarios.json` and `expected/sample.json` to `sample/src/main/assets/parity/`
(the `WebParityTest` unit test fails if the copies differ).

## How the SDKs are checked

- `WebParityTest` (JVM): replays the scenarios with the page sizes the web SDK measured.
- Sample app → **Cek paritas**: replays them on a device with the real `PdfRenderer` page sizes.

## Web SDK 1.1.2 bugs found while building the runner

1. `createViewer({ container: element })` fails ("invalid container"): the config deep merge copies
   the HTMLElement into a plain object. A selector string works.
2. `destroy()` throws while thumbnails are still rendering: it calls `.catch` on pdf.js 4's
   `RenderTask.cancel()`, which returns nothing.
3. Placing an item with the default (centered) position on a page that has not been rendered yet
   centers it on a 300 × 150 canvas (browser default size), so it lands near the top-left.

The web SDK also measures pages from the integer canvas size, e.g. A4 becomes 594.67 × 841.33 pt
instead of 595.28 × 841.89. The mobile SDKs use the real page size; the difference stays well
inside the 0.5 pt tolerance.
